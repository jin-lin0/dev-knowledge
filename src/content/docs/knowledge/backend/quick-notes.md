## HTTP 路由与异常

### HTTP 429、RPM 与并发数是不同约束

HTTP 429 表示服务端按某种时间窗口限制了请求频率；具体按账号、资源还是共享配额统计，要看服务端契约，不能仅凭一次错误反推出额度。RPM 指每分钟请求数，并发数限制的是同时在途的任务数；一个业务任务还可能发出多次模型或接口请求。[RFC 6585：429](https://www.rfc-editor.org/rfc/rfc6585#section-4)

- **重试等待**：响应可以携带 `Retry-After`，值为等待秒数或 HTTP 日期；只做几百毫秒退避，可能在服务要求等待几十秒时提前耗尽尝试次数。响应正文中的等待提示属于服务专用协议，不等同于标准头。[RFC 9110：Retry-After](https://httpwg.org/specs/rfc9110.html#field.retry-after)
- **调度边界**：降低并发通常能减轻突发压力，但不等于实现每分钟限速。一个任务失败后立即派发下一个任务，也可能在同一冷却窗口继续触发 429；设计时需分别考虑请求级重试和共享配额范围内的限速或冷却。
- **任务与请求的换算**：若每个任务平均需要 k 次模型请求，R RPM 对应的任务吞吐上限约为 R/k 个任务每分钟，尚未扣除其他流量与重试。均匀发送时，平均请求间隔需不小于 60/R 秒；这是速率预算，不是每个请求必须执行这么久。限速应覆盖实际 API 调用与重试，不能只按任务启动次数计数。
- **RPM 与 TPM 独立**：TPM 是每分钟 Token 额度，与请求次数是两种限制；Token 消耗较少也可能先触发 RPM。具体时间窗口、Token 估算方式及限额共享范围由服务端定义，不能仅凭客户端 Token 汇总证明未触发服务端 TPM。作为公开协议实例，[Claude API 限流说明](https://platform.claude.com/docs/en/api/rate-limits#rate-limits)分别定义请求频率、输入和输出 Token 限额，并说明 Token 估算及缓存口径；这些具体规则不能直接套到其他网关。
- **结果解释**：限流导致的执行无效应与任务质量失败分开统计；只对少量成功执行样本计算出的均分，不能代表整批任务质量。
- **框架排障链接不代表错误起源**：LangChain 可以在收到的 HTTP 429 错误上追加 `lc_error_code=MODEL_RATE_LIMIT` 和自身文档链接；这一步只是分类与补充说明，不是在客户端计算 RPM 阈值。应沿调用链核对原始响应状态、响应正文和包装函数，不能因为链接域名属于框架，就认定限制由框架设置。2026-10-15 核验 `@langchain/openai@1.4.5` 的错误包装器和 `openai@6.37.0` 的 HTTP 错误构造逻辑；[LangChain 官方说明](https://docs.langchain.com/oss/javascript/langchain/errors/MODEL_RATE_LIMIT/)也将其解释为模型服务方的请求频率限制。
- **验证**：2026-10-15 核对上述 HTTP 标准，并对照有界并发调度、有限重试和无效样本聚合的实际控制流确认三者的职责边界。

### HTTP `500`、`502`、`504` 与测试错误中间件

`500` 表示服务端遇到无法完成请求的意外情况；服务作为网关收到无效的上游响应时用 `502`，等待必需的上游响应超时时用 `504`。正常空结果或输入错误应按接口自己的资源契约处理，不能只因为没有拿到数据就统一返回 `500`。[RFC 9110 服务端错误语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6)

- **定位方式**：同时读取状态码、响应体和抛错位置。没有显式分类的异常可能落入应用的默认 `500`，不能仅凭状态码判断是上游故障还是本地解析错误。
- **测试边界**：测试错误中间件要复用生产实现或匹配其状态码与响应协议。测试默认映射 `502`、生产默认映射 `500` 时，测试通过仍不能证明真实接口会返回 `502`。
- **验证**：2026-10-11 对照实际服务错误响应与测试兜底逻辑，并通过模拟上游响应、无效 JSON 和取消请求验证显式分类后的 `502`、`504`；实际有效请求恢复为 `200`。

### 服务级 context 与请求级 context

`context` 通常只是程序给普通上下文对象起的名字，没有自动创建状态或管理生命周期的语言机制；要看对象在哪里创建、传给了谁。

- **服务级上下文**：在服务启动时组装依赖、配置与进程内状态，由该实例的多个路由共享。它便于复用连接和服务，也方便测试注入替身。
- **可选依赖参数（dependency injection）**：生产入口使用默认实现，不代表依赖参数冗余。测试可能借它替换数据库、外部服务或执行器；判断能否删除时要检查所有调用方以及默认实现的副作用。若改用模块 mock 或工厂组装，需要同步迁移测试，不能只删函数参数。
- **资源所有权**：接收外部连接与内部创建连接应有明确的关闭约定。例如内部创建的连接由当前调用在 `finally` 关闭，外部传入的共享连接由调用方管理。重构注入入口时，要一起保留这个生命周期语义。
- **请求级上下文**：每次请求单独创建，保存该次请求、响应、解析后的 URL 等信息。不能仅因两者都叫 context，就认为生命周期相同。
- **状态边界**：进程内 Map、取消控制器与进行中的 Promise 不等于持久化数据；重启后能否恢复任务，需要额外的存储与恢复机制。
- **类型边界**：TypeScript 的 interface 只约束对象形状。仅包含接口、类型别名及 type imports 的文件，不会因为被导入就生成对应的运行时对象。
- **来源**：2026-09-10 对照服务启动、路由参数传递和关闭流程核验；本地 TypeScript 转译验证只含上述类型声明的模块仅保留模块标记，没有业务对象初始化。
- **依赖注入验证**：2026-10-13 对照执行入口、默认依赖创建、测试调用和 `finally` 分支核验：生产调用省略依赖对象，测试显式传入替身，并断言外部连接未被执行入口关闭；此处为源码核验，未重新运行该测试。

### NestJS `Cannot GET /path`：路由兜底 404

当堆栈指向 NestJS `routes-resolver` 的 `registerNotFoundHandler` 回调，且错误为 `NotFoundException: Cannot GET /path`，表示该请求落入路由未匹配的兜底处理。它与已命中业务接口后抛出的“资源不存在”404，需要结合堆栈与路由上下文区分。

- 这条堆栈可以定位异常产生的位置，不能识别发起请求的人或服务，也不能单独证明服务崩溃、受到攻击或某次业务执行失败。
- 全局异常过滤器可以捕获这种异常；是否写日志、是否发送群通知，取决于应用策略，不能仅根据 `WARN` 推断不会通知。
- 核对服务地址、请求方法、全局前缀与实际注册路由；需要定位来源时查看访问日志中的连接来源、请求 ID、User-Agent 和代理链。代理后的连接地址可能只是网关；不能把未经可信代理校验的 `X-Forwarded-For` 直接当真实来源。
- **来源**：[NestJS v11.1.12 路由兜底源码](https://github.com/nestjs/nest/blob/v11.1.12/packages/core/router/routes-resolver.ts#L136-L150)、[NestJS 异常过滤器](https://docs.nestjs.com/exception-filters)、[Express 代理信任配置](https://expressjs.com/en/guide/behind-proxies/)。本条验证日期：2026-09-08。

### Node.js `server.close()` 会回收空闲连接

从 Node.js 19 起，HTTP `server.close()` 会停止接受新连接，并回收当前未在发送请求或等待响应的空闲连接；使用 keep-alive 不代表调用 close 后这些连接一定继续阻塞退出。

- **边界**：活跃请求、升级连接和 WebSocket 的关闭是另外的问题，不能把空闲连接回收等同于所有网络任务都已停止。为旧版本兼容增加 `closeIdleConnections()` 时，应先确认实际 Node.js 版本。
- **验证**：2026-10-13 在 Node.js 24.19.0 中，用启用 keep-alive 的 HTTP Agent 完成请求，保留 Agent 并调用 server.close，关闭回调正常完成，无需先销毁 Agent 或额外调用 closeIdleConnections。
- **来源**：[Node.js HTTP server.close](https://nodejs.org/api/http.html#serverclosecallback)的版本历史和连接关闭约定。

## 身份认证与云资源

### Vercel 项目改名与 OIDC 身份联合

OIDC 身份联合让外部服务根据 Vercel 签发的身份令牌授予访问权限。令牌包含项目名，`sub` 也含项目名；改名后，若云端信任策略仍匹配旧名称，认证可能失败。出现改名提醒并不能证明应用已使用 OIDC，也不能据此推断它在使用 Cloudflare。[Vercel OIDC 改名说明](https://vercel.com/docs/oidc/reference#team-and-project-name-changes)

- **判断实际影响**：检查代码与基础设施配置是否读取 Vercel OIDC 令牌、交换短期凭据，或按其 claims 授权；还需核对云端信任策略。只看项目依赖名称不够。
- **与静态密钥区分**：显式使用 Access Key ID / Secret Access Key 访问 R2 的 S3 API，不依赖 Vercel 项目名声明；使用 AWS SDK 也不代表启用了 AWS OIDC 身份联合。[Cloudflare R2 认证](https://developers.cloudflare.com/r2/api/tokens/)
- **域名另行核对**：项目 ID 与名称不同。改名后新生成的 `vercel.app` 地址使用新名称，旧地址不保证继续可用；自定义域名独立分配，仍需核对绑定。已保存的旧 URL、回调及跨项目调用地址不会自动改写。[Vercel 项目改名指南](https://vercel.com/kb/guide/how-do-i-change-the-name-of-my-vercel-project)
- **验证**：2026-10-19 对照官方 claims 定义、R2 凭据接口和改名指南；仓库检查只能说明代码使用的认证方式，不能代替云控制台的策略核验。

## 接口输入校验

### 草稿校验与提交、发布或执行校验

允许保存未完成内容时，区分“当前数据可以合法保存”和“内容已经完整到可以提交或执行”。草稿仍检查身份、字段类型、范围与已填写的嵌套结构；提交或执行阶段再要求业务必需内容齐全。例如空正文和空检查项可以是合法草稿，但不能直接执行。

- **设计选择**：两个校验阶段不必对应两份独立字段定义。可以共用基础 Schema，再派生完整 Schema，或用一个校验入口按阶段追加完整性规则；独立的运行类型可把草稿可选字段变成执行必填字段，非空约束仍由运行时解析保证。完整 Schema 已继承全部适用约束时，按阶段选择一个 Schema 解析，避免两次 parse 重复应用 transform。只有保存与执行规则确实相同时，才可直接复用同一套校验。
- **容易误用**：Zod 的 `.partial()` 只让字段可省略，不会取消已经提供字段的 `.min(1)` 等规则，所以不能自动把严格提交 Schema 变成接受空字符串、空数组的草稿 Schema。需要显式定义允许的未完成形态。
- **共同边界**：新字段应进入公共定义或两阶段的允许字段集合；严格草稿校验先拒绝未知字段时，后续完整校验不会有机会接受它。运行前重新校验当前资产，避免把旧的“已发布”状态当成当前规则下的有效性证明。
- **Schema 与额外校验函数**：Zod 的 `.refine()`、`.superRefine()` 可以表达字段关系和场景限制，Schema 的职责不局限于字段类型。纯数据规则可集中到场景 Schema，独立校验钩子是组织方式而非必需能力；只有明确需要独立依赖、领域错误协议或复用边界时，再评估保留。移动规则时还要核对错误类别、字段定位、空值与默认值的行为。
- **来源与验证**：[Zod 对象 Schema、`.partial()` 与扩展规则](https://zod.dev/api)。2026-10-12 以通用任务对象做独立 Node.js 实验：空正文和空检查项通过草稿校验、被完整校验及其 `.partial()` 拒绝，补齐内容后通过；错误字段类型与未知字段在草稿阶段仍被拒绝。上述阶段划分与复用方式属于基于这些机制的设计建议。
- **细化规则验证**：同日以通用消息草稿验证：共享 Schema 接受非空历史，追加 `.superRefine()` 的场景 Schema 拒绝并定位到 history；空正文且未填历史的草稿仍可保存。该实验只验证数据校验能力，不证明迁移现有领域错误协议后行为完全相同。
- **转换次数验证**：同日以名称末尾追加字符的转换规则验证：派生完整 Schema 保留转换，按阶段选择 Schema 后结果只追加一次；校验阶段不能默认假定所有转换都具有幂等性。

## 接口数据归一化

### 请求参数不等于响应的数据口径

HTTP 请求成功、URL 带有目标模式参数，都不能单独证明服务端按该模式返回了数据。对单位、调整方式、身份范围等有明确要求时，应核对端点契约、响应声明并读取协议允许的字段；缺少符合契约的数据就拒绝，不能只改标签把其他口径的数据当作目标口径。

- **记忆点**：字段都有日期和数值、能画图或能通过类型检查，只能证明结构可用，不能证明数值含义一致。声明、字段选择和实际数据需要共同核验。
- **字段边界**：当前协议允许同一模式使用多种字段名时，应解析这些有效表达；字段前缀本身不能证明或否定数据口径。已存在的优先字段若格式损坏，则应报错，而不是改读另一字段掩盖异常。
- **验证**：2026-10-11 对公开数据端点做对照请求，确认不同端点的同一历史记录数值不同；随后对照[上游自身的图表解析实现](https://st.gtimg.com/quotes/hs-fund/zxgweb-chart-5878585c4a61.js)，核验专用接口支持多种字段表达。模拟协议测试覆盖有效字段、优先字段损坏与空序列的区别。

### 数据的事件时间不等于信息可用时间

历史回放、模拟和评估需要区分记录描述的事件时间与记录完整可获取的时间。聚合结果可以标注周期起点，却直到周期结束才定稿；只检查事件时间早于决策时间，仍可能使用当时不可知的最终数据，产生前视偏差。

- **时序约束**：输入可用时间 ≤ 决策时间 ≤ 操作执行时间。同一周期内执行操作可以成立，但决策应使用执行前已经可用的快照；部分数据与最终聚合结果不一定给出相同结论。
- **模型边界**：明确声明使用最终数据近似更早的决策与执行，属于模拟假设。可配置开关和假设标签能说明口径，不能自动证明当时真实可执行；状态或持有期限限制则是另一项独立约束。
- **验证**：2026-10-11 在 Node.js 中构造事件时间相同、可用时间不同的部分与最终快照，验证决策时只可读取部分快照，且两个快照会产生相反的阈值判断。

### 删除历史兼容不等于删除数据校验

历史兼容把旧字段、旧持久化键或旧入口转换成当前协议；边界校验检查当前协议的数据是否合法。删除旧格式读取和方法别名后，仍应保留身份核对、无效数据拒绝与请求失败处理。

- **必填元数据**：协议承诺由服务端确认的状态或时间，缺失时应按协议错误处理；客户端的本地推算不能替代服务端确认。可选字段的正常默认值则要按当前契约判断，不能把所有 `??` 或错误处理都视为兼容代码。
- **单一路径**：未发布协议是否需要旧格式转换，参见[未发布本地产物的兼容边界](/knowledge/backend/trustworthy-agent-evaluation/#yaml-和-json-是编写体验选择不是可信边界)。当前上游确实提供多种格式时，输入适配仍属于正常接入职责。
- **验证**：2026-10-11 对照协议读取控制流，并用依赖注入实验确认：响应缺少约定元数据时，默认推算分支仍返回成功，因此会掩盖协议缺失；这与显式拒绝无效输入的校验职责不同。

### `Number(null)` 不能用来识别缺失数值

`Number(null)`、`Number('')` 和 `Number('   ')` 都得到 `0`，随后 `Number.isFinite()` 仍返回 `true`。所以“先转数字再判断有限”能排除 `NaN`、无穷大，却不能区分真实零值与缺失值。

```ts
function finiteOrNull(value: unknown): number | null {
  if (typeof value !== 'number' && typeof value !== 'string') return null;
  if (typeof value === 'string' && value.trim() === '') return null;
  const number = Number(value);
  return Number.isFinite(number) ? number : null;
}
```

- **记忆点**：真实的 `0` 和 `'0'` 应保留；缺失值保留为 `null`，展示为缺失，并避免进入依赖该字段的评分或统计。
- **覆盖率边界**：对象存在不等于字段可用。覆盖率应按有效字段、时间范围与接口状态计算；查询成功但没有匹配记录，也不能自动等同于请求失败。
- **来源**：[ECMAScript 数值转换规范](https://tc39.es/ecma262/2024/#sec-tonumber)、[字符串数值转换](https://tc39.es/ecma262/2024/#sec-stringtonumber)。2026-10-10 在 Node.js 24.19.0 验证上述强制转换，并以模拟 HTTP 数据验证显式 `null` 经未经缺失检查的转换后成为 `0`。

### JSON 裸数字 ID 可能在解析时失去精度

JavaScript 的安全整数范围是 `-(2^53 - 1)` 到 `2^53 - 1`。JSON 中未加引号的大整数 ID 进入 `JSON.parse` 时可能已经被舍入，之后再用 `String()` 或 `BigInt()` 转换也无法找回原始数字。

```js
JSON.parse('{"id":9007199254740993}').id;   // 9007199254740992
JSON.parse('{"id":"9007199254740993"}').id; // '9007199254740993'
```

- **接口契约**：不参与运算的长 ID 优先用字符串传输。确需读取裸数字时，应在转换成 Number 之前保留数字源文本；不能对已经舍入的值调用 `toString()` 冒充恢复精度，也不能误改原本处于引号内的文本。
- **边界**：已经作为 Number 传入的失真值无法由下游恢复；任意精度小数与大整数 ID 也是不同需求，保留大整数不代表实现了完整的高精度数值计算。
- **来源**：[ECMAScript 的安全整数定义](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-number.max_safe_integer)。2026-10-15 在 Node.js 中验证裸数字与字符串 ID 的解析差异，并测试正负大整数、指数写法、普通数值及引号内文本。

### `confidence` 百分比不自动代表经过校准的成功概率

接口中的 `confidence`、`score` 或 `likelihood` 只是字段名称。检查数值在 0–1 范围、乘以 100 并显示为百分比，验证的是输入范围和展示格式；这不能证明数值与实际发生频率一致。

- **语义边界**：先确认它衡量的是文本分类、事件真实性、未来发生概率，还是规则评分。展示分级的阈值也不能自动视为提醒触发阈值或统计置信区间。
- **概率校准**：如果要把预测值 0.8 解释成长期约 80% 的事件发生率，需要用独立历史结果检验预测概率与观察频率的关系。某一条记录的分数高，不能代替这类检验。
- **来源**：[scikit-learn 概率校准说明](https://scikit-learn.org/stable/modules/calibration.html)。2026-10-11 用独立 Node.js 实验验证 0.88 的百分比格式化得到 88，而格式化过程并未读取任何真实结果或校准样本。

### 来源限定的 ID 需要保留命名空间

如果上游 ID 只在某个来源、租户或资源范围内唯一，归一化时就要保留这个范围。只保留短 ID，可能让请求路由、缓存或持久化索引指向另一条记录。

```js
const keyOf = ({ scope, id }) => JSON.stringify([scope, id]);
const records = [
  { scope: 'alpha', id: '001' },
  { scope: 'beta', id: '001' },
];
const byKey = new Map(records.map(record => [keyOf(record), record]));
```

- **边界**：需要保留的是决定身份和路由的维度，并非所有系统都需要同一组字段。已有全局唯一 ID 时可直接使用它；标识组合应使用确定的编码，不能把显示名称当作唯一标识。
- **验证**：2026-10-11 在 Node.js 24.19.0 验证同短 ID、不同范围的两条记录：只按 ID 建 Map 后仅剩一条；使用范围与 ID 的组合键后保留两条。API 调用方不能在传递过程中丢掉上游提供的身份范围。

## 数据采集与上游依赖

### RSS 转换器开源，不代表上游数据免费可用

输出 RSS 只改变下游读取的格式，不会取消采集端需要的授权、配额或费用。评估订阅通知方案时，应分别核对上游访问、内容转换、定时运行和消息发送的条件；某个环节有免费额度，不代表整条流程免费。

- **验证边界**：工具支持一条路由，不代表某个公开实例当前可用。选定实例后仍需实测身份认证、返回内容和连续更新，不能仅凭文档中的示例地址承诺稳定服务。
- **来源**：2026-10-11 核对 [RSSHub 的 X 接入选择逻辑](https://github.com/DIYgod/RSSHub/blob/master/lib/routes/twitter/api/index.ts)：接入依据网页授权、第三方接口或开发者凭据选择实现，未配置时初始化报错。[X API 官方计费说明](https://docs.x.com/x-api/getting-started/pricing)另行规定上游资源访问费用，具体价格需按使用时的官方说明确认。

### 检测到事件不等于通知发送成功

去重状态应区分“已发现”“待发送”和“发送已成功受理”。在权限检查或网络发送前就把事件记为已处理，可能让拒绝、失败或程序退出后的重试被跳过。

- **处理方式**：新事件先进入待发送状态，按投递结果更新；暂时失败的事件继续保留，允许后续重试。只与上一次采集结果做差集，不能代替待发送队列。
- **确认边界**：邮件 API 成功受理，不代表邮件已经到达收件箱；操作系统成功添加通知请求，也不代表用户已经看到通知。状态名和承诺应对应实际拿到的确认层级。
- **验证**：2026-10-11 用独立 Node.js 实验验证先写去重标记、再拒绝投递的顺序：第二次允许投递时，事件仍被去重跳过。结论适用于通知、邮件和其他事件驱动的外部操作，不等同于验证了某个具体运行环境的失败原因。

## 数据生命周期

### 普通 SELECT 后再写入，不自动构成原子判断

两个实例都可能先查到“没有运行任务”或“任务仍待执行”，随后各自启动。因此，数据库可共享状态，但独立的查询与写入并不能自动保证只有一个执行者。

- **领取同一任务**：可用针对已有任务行的条件更新，只有状态转换成功的一方执行；或者在短事务内锁定候选任务并提交领取状态。
- **限制同一资源上的多个任务**：需要对相同调度范围或资源位进行互斥、容量控制；分别锁住不同任务行，不会自动形成全局并发上限。
- **计数配额**：同一范围内的新增操作可以先在短事务中锁定一条确实存在的共享父记录，再检查当前条数并写入；所有新增路径都须遵守相同的锁顺序。先插入、超额后再删除会短暂暴露未获准的记录，并可能删掉另一并发请求刚确认的更新。2026-10-15 以两个请求争夺最后一个名额的控制流回归验证这一边界；数据库行锁语义依据下列官方文档，模拟测试不代替真实数据库并发验证。
- **事务边界**：锁只覆盖领取与状态变更，不应持有数据库事务等待远端长任务完成。
- **来源**：[MySQL InnoDB Locking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html) 明确说明普通 SELECT 后再插入或更新不足以防止其他事务修改数据；结合任务领取与执行分离的源码路径核验于 2026-09-10。

### 连接错误不证明写入未提交

服务端可能已经提交写入，只是在成功响应到达客户端之前连接断开；单条语句原子性不能据此证明重放安全。

- **处理方式**：把明确回滚与结果未知分开；计数累加等非幂等写入不能在结果未知时无条件重试。需要可靠重试时，应使用稳定操作 ID、去重记录或可查询的提交状态。
- **验证**：2026-10-15 用“先累加服务端状态、再拒绝响应 Promise”的替身验证：无条件退回另一条累加路径会重复计数；只记录未确认结果不会再执行第二次累加。这是故障模型验证，不是特定数据库故障发生频率的证据。

### `deleted_at`：软删除、回收站与文件删除

软删除（逻辑删除）保留数据库记录，只改变它是否出现在正常查询中；物理删除才移除记录。`deleted_at` 是常见约定，不是数据库自动赋予功能的特殊字段。

- 正常列表筛选 `deleted_at IS NULL`；移入回收站时写入删除时间。
- 回收站筛选 `deleted_at IS NOT NULL`；恢复时把该字段设回 `NULL`。
- 列表和详情接口都需要遵守删除状态及访问权限；仅增加一列不会自动生成回收站页面或恢复接口。
- Sequelize v6 可以通过 `paranoid: true` 实现这类行为，需要启用 timestamps；原始 SQL 不会自动补充软删除过滤。详见 [Sequelize Paranoid 文档](https://sequelize.org/docs/v6/core-concepts/paranoid/)。

如果记录只是引用外部文件的 URL，更新删除标记本身不会删除文件，也不会撤销该 URL 的访问。文件清理与 CDN 缓存失效需要另外处理，不能把“从列表隐藏”描述成“文件已经彻底删除”。例如 CloudFront 的缓存失效会让后续请求重新访问源站，不等于删除源站对象；客户端已有缓存也不一定同时失效。详见 [CloudFront 缓存失效说明](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html)。
